## 取得方法

1. サイト固有の本文領域（該当ホストの場合）。
2. articleBodyやブログの本文コンテナ。
3. Readabilityによる汎用抽出。
4. DOMから本文を得られない場合、公開JSON-LDのarticleBodyを利用。description（要約）を全文の代わりに使わない。会員・有料と明示された場合、このフォールバックを行わない。
5. URL取得ができない場合、文章の共有・貼り付け、保存HTMLの端末内抽出、画像OCRを利用する。

段落、見出し、表のセルの区切りを保つ。本文中の図のキャプションは残し、図・写真・表を含む場合は元記事へのリンクと注意を出す。短い結果は記事の一部である可能性を明示する。ログイン情報や購読者Cookieは取得サーバーに送らない。

## 過去HTMLの検証

Mozilla Readabilityリポジトリのコミット `ab4027a8b37669745016869a37a504727992b2ba` の `test/test-pages` を使用。本文そのものはこのリポジトリへ転載せず、結果だけを `verification/snapshots-2026-11-06.json` に保存した。

6件すべてで、40文字以上の期待段落163/163を保持し、空白を除いた全体文字数も期待結果と一致。これは同一文字列・意味理解・現在のレイアウトの完全保証ではない。WordPressは初回に関連記事等が混ざり4,431文字だったが、Jetpackの共有・関連記事領域を除去し、期待する3,005文字になった。

## Android共有と保存HTML

PWAマニフェスト・Service Workerを追加。共有文章をPOSTで端末内に受け、使い捨てのローカル保存を介してアプリへ渡す。URLクエリに共有文章を入れない。アプリの基本ファイルだけをキャッシュし、記事API応答や画像をキャッシュしない。

Chromium上で共有POSTがサーバーへ到達しないこと、共有後に文章が削除されること、URL共有ではAPIへ進むことを確認。マニフェスト解析エラーなし。Android実機のインストール・OS共有メニュー表示は未確認。スクリーンショット共有、常駐ボタン、他アプリの画面取得は今回未実装。

保存HTMLは隔離したDocumentで処理し、実画面へHTMLを挿入せず、文字列だけを表示する。スクリプト実行と外部画像・CSS・iframeへの通信が発生しないことをブラウザテストで確認。Android Chrome等で保存されるMHTMLやPDFは対象外。

## 最終確認

- `npm run build` 成功。
- ユニット・HTTPテスト31件、ブラウザテスト8件成功。
- 320px・390px・1440pxで横方向へのはみ出しなし。
- 新APIのローカルHTTP入口へ実際にPOSTし、GitHubの公開READMEを外部取得して200応答。APIバージョンarticle-v3、6,646文字、InstallationからLicenseまで主要見出しを確認（`verification/local-api-2026-11-06.json`）。Vercel公開先の検証とは別。
- URL解決も含めて取得全体に15秒の待ち時間上限を適用。アプリ本体の再取得が遅い場合は、3.5秒で保存済みの基本画面へフォールバックする。画像OCRモデルはこの基本画面のキャッシュに含めない。
